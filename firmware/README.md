# Firmware

## Toolchain setup

Use ESP-IDF **5.5.5**, Python 3, Git, and the host build tools required by IDF.
The wrapper expects the toolchain under the repository's ignored `.tools` folder.
From the repository root, on a machine with those prerequisites installed:

```sh
mkdir -p .tools
git clone --branch v5.5.5 --recursive https://github.com/espressif/esp-idf.git .tools/esp-idf
python3 -m venv .tools/python
.tools/python/bin/python -m pip install 'cmake==3.30.9' 'esptool==5.3.1'
PATH="$PWD/.tools/python/bin:$PATH" IDF_TOOLS_PATH="$PWD/.tools/espressif" \
  .tools/esp-idf/install.sh esp32s3
```

These commands download and install dependencies; run them only during initial
setup. Do not replace an existing installation or private pair configuration.
The flash helper requires esptool 5 (validated with 5.3.1); use
`.tools/python/bin/python` after the setup above, or your normal Python if it
already provides esptool 5. The ESP-IDF environment bundles esptool 4 and cannot
run this helper.
Component manifests and `dependencies.lock` files pin TinyUSB and LED dependencies.
Provision the pair using [setup steps 3–4](../docs/SETUP.md) before building.

## Build and provision

Build each ESP32-S3 DevKitC image from its role directory with the project-local
ESP-IDF wrapper:

```sh
firmware/tools/idf.sh -C firmware/bridge-b build
firmware/tools/idf.sh -C firmware/bridge-a build
```

`bridge-b` is the native-USB HID keyboard. `bridge-a` is the native-USB CDC
endpoint. Both deployable builds require `config/private/pair_config.h`, which
is generated by `firmware/tools/provision.py`; it contains the pair MACs
and ESP-NOW keys and is intentionally ignored by Git.

The targets require ESP32-S3 hardware with 16 MiB flash and at least 8 MiB
PSRAM. At boot they check those values and check the provisioned Wi-Fi MAC
against eFuse before enabling the radio. UART0 accepts `status`, `identify on`,
and `identify off` for maintenance over the labelled COM/UART USB-C connector.

For a compilation-only fixture, use a separate build directory and empty
temporary sdkconfig so it cannot inherit a deployable configuration:

```sh
: > /tmp/bridge-fixture.sdkconfig
firmware/tools/idf.sh -C firmware/bridge-b -B /tmp/bridge-b-fixture \
  -D SDKCONFIG=/tmp/bridge-fixture.sdkconfig \
  -D 'SDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.defaults.fixture' build
```

Fixture images compile against public dummy values and deliberately omit
ESP-NOW transmission and HID report submission. They are not flashable release
artifacts.

Host session checks (no board or keys required):

```sh
cc -Wall -Wextra -Werror -Ifirmware/common/include \
  firmware/tests/test_session.c firmware/common/bridge_session.c -o /tmp/bridge-session-test
/tmp/bridge-session-test
rm /tmp/bridge-session-test
python3 -m unittest discover -s firmware/tools -p 'test_*.py'
```

B briefly disconnects and re-enumerates after USB suspend so a retained pressed
report cannot be delivered ahead of the released state. Capture remains paused
until the app starts a new session. Target suspend/recovery testing is required.
The stack uses Espressif's [USB device event API](https://docs.espressif.com/projects/esp-usb/en/latest/esp32s3/usb_device.html).

## Indicators and verification

Use the labels on the board: COM/UART is for flashing and maintenance, USB/OTG is
for normal operation. `identify on` produces one magenta pulse for A and two for B.
GPIO48 has been visibly verified on the tested pair; other revisions can use GPIO38.

| State | Device RGB | Pattern |
| --- | --- | --- |
| Boot | `(16,8,64)` | 150 ms on / 250 ms off |
| Searching | `(0,64,0)` | 300 ms on / 700 ms off |
| Connected and paused | `(0,64,0)` | Steady, stays illuminated |
| Active connection | `(0,24,64)` | Steady |
| Activity | `(64,59,24)` | Brief pulse |
| No peer after one minute | `(64,18,0)` | 400 ms on / 1600 ms off |
| Critical error | `(64,0,0)` | 120 ms on / 120 ms off |

The ordinary status LED sleeps after five minutes; paused, error and identification
indications remain visible. Flashing uses `tools/flash.py`, which verifies every
written image and saves ignored, pair-specific receipts. Opening COM/UART resets
these boards; the UART helper waits for maintenance startup before sending commands.

Boot diagnostics latch the firmware timer after local USB/radio initialization
returns. They exclude host enumeration delays; `radio-ready` is latched separately
at successful ESP-NOW setup. Read the values with UART `status` or app debug mode.
No measured maximum boot time or latency is claimed; see the requirements record.
